Inheriting Complexity: Rethinking the Architecture Behind Prosale

RivendellAI’s journey maintaining and modernizing a legacy Angular and .NET estate management platform.

How RivendellAI is modernizing an estate sale platform weighed down by fragmented frontend code and tangled backend synchronization

When we at RivendellAI took over the Prosale.com platform, we stepped into a system that’s been serving real-world customers for years. It’s an ambitious web-based estate sale management tool, written primarily in Angular and .NET, and it does a lot of things well—inventory tracking, barcoding, user management, pricing, sales, photo uploads, mobile workflows.

But once we opened the hood, it became clear that the architecture had grown more accidental than intentional. Feature by feature, fix by fix, things got bolted on—until the system became difficult to evolve, debug, or even understand.

This blog post digs into two of the biggest pain points we inherited: the overly fragmented Angular frontend, and a microservice backend split across 16 separate databases. Spoiler: we’re actively fixing both.

Frontend: Death by a Thousand Components

We’re not against Angular. Used correctly, it’s a powerful tool. But the way the frontend was structured in Prosale borders on self-sabotage.

Let’s say we want to debug a single screen—a typical “Edit Product” page. Here’s what that actually means in Angular world:

  • A parent component shell

  • Child components for the form, the image gallery, the pricing logic, the availability toggle, etc.

  • Each component has three files: .ts, .html, and .css

  • Then there’s the routing module that lives somewhere else entirely

  • And service classes (sometimes reused, sometimes rewritten) that handle all API calls, often with state-dependent behavior buried in the component logic

  • Throw in some observables, subscriptions, maybe a shared state service, and a bunch of @Input()/@Output() bindings

  • Oh, and one wrong click might trigger a cascade of async calls buried across 5+ services

So now we’re 30–50 files deep, trying to understand what is functionally one screen.

Debugging that? It’s like trying to trace a fuse box while blindfolded—except the wiring keeps moving.

This isn’t “component reuse.” It’s accidental complexity. Abstraction for abstraction’s sake. A UI shouldn’t require a small novel’s worth of code and config just to update a button.

We’re slowly consolidating this mess:

  • Reducing unnecessary nesting

  • Moving toward standalone components (now possible in Angular 13+)

  • Introducing feature modules with clearly scoped responsibilities

  • Avoiding shared service bloat by defining tighter domain-specific interfaces

We’re also open to going non-Angular for future frontends. Blazor, Qwik, Qute, Thymeleaf—all on the table.

Backend: Microservices Without a Map

On the backend, things start out promising. The .NET code is organized in a fairly standard microservice style—clean service layers, REST endpoints, some use of dependency injection.

But here’s the kicker: 16 separate databases, each tied to its own service or functional area. And they’re not isolated—they depend on each other.

To keep things synchronized, a message bus was introduced, mimicking a pub/sub architecture. In theory, this should provide a decoupled, scalable flow of events.

In practice? It’s a tangled mess of partial subscribers, unclear ownership of events, and no single source of truth. One service publishes a product update, five others listen and react—but often in subtly different ways. Debugging it takes days. You’re not fixing code—you’re tracing a ghost through multiple logs, waiting for a reproduction that may or may not happen.

Some problems we’ve faced:

  • Circular dependencies between events

  • Multiple services racing to update the same entity in their own silo

  • Data inconsistencies when one subscriber fails silently

  • The need for eventual consistency in a system designed as if everything is real-time

The architecture is trying to scale before it stabilized.

Framework Fragility: The Hidden Cost of Dependencies

Another major blocker to progress? Third-party dependency lock-in.

When we began upgrading Angular from version 8 toward current (v13+ and eventually v17), we ran into a wall—many of the third-party libraries that the UI depended on were either:

  • No longer maintained

  • Incompatible with Ivy or standalone components

  • Replaced with entirely different APIs

  • Removed from NPM altogether

This means that seemingly simple upgrades require rewriting entire modules just to stay on a supported version of Angular. For example, UI libraries like ng2-smart-table, date pickers, file upload components, or barcode renderers may not have a drop-in replacement anymore.

Worse, some of these libraries are deeply embedded—touching multiple components and service layers. You don’t just swap it out. You rebuild and retest everything around it.

This reliance on community packages that lack long-term support is a silent debt—and it accumulates interest fast.

We’re actively working to untangle this:

  • Removing fragile dependencies in favor of native Angular tools or internally maintained wrappers

  • Choosing libraries with strong community backing and clear upgrade paths

  • For core UI elements, building lightweight, reusable components ourselves

  • Embracing the new Angular standalone APIs to cut down boilerplate and simplify integration

The long-term goal? A UI stack we own, not one we constantly chase.

Our Approach Moving Forward

We’re not going scorched-earth on this system. It works, customers rely on it, and there’s real domain knowledge baked in. But we are bringing clarity and intentionality to the table:

  • We’re moving to domain-aligned service boundaries, not arbitrary ones

  • Consolidating databases where justified (not every service needs its own schema)

  • Simplifying the message bus model—fewer publishers, more clearly defined contracts

  • Adding observability: tracing, correlation IDs, meaningful logs

  • Replacing tightly-coupled shared services with domain gateways

And critically, we’re designing new subsystems—like Consignment—in Quarkus, our preferred stack for lightweight, fast, modern APIs. These services are purpose-built, easier to deploy, and don’t rely on massive shared state.

Why This Matters

We’re not just cleaning house for fun. A better architecture enables:

  • Faster feature development

  • Shorter onboarding time for new engineers

  • Reduced support incidents

  • Cleaner testing strategies

  • A more stable, scalable foundation for mobile and multi-tenant evolution

Prosale can’t be stuck in a 2015 web monolith world. It’s time to evolve—from legacy platform to modern estate sale management SaaS.

Closing Thoughts

Maintaining legacy systems means balancing respect for what works with courage to challenge what doesn’t. At RivendellAI, we believe architecture should serve the team, the users, and the future—not just the past.

This is just the start of the journey. In the next post, we’ll share how we built the new Consignment subsystem in Quarkus—and why we think it’s a template for everything that comes next.
